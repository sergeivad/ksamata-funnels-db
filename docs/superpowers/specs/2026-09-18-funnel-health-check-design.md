# Пилюля «Проверить» в списке воронок — состояние ссылок воронки

**Дата:** 2026-09-18 · **Статус:** спека к реализации

## Задача

В списке воронок рядом со статусом должна появляться пилюля «Проверить» у той
воронки, у которой что-то не отвечает, — и она же должна уметь запустить
проверку. Эталонный случай, названный владельцем: у **F101 комнаты не
существуют**, и сейчас об этом не говорит ничто.

## Замеры, на которых стоит решение

Все числа — по живой базе (79 воронок, 59 активных) и по живым страницам,
18.09.2026. Прод на этот день держит 85 воронок; пропорции те же.

### Почему F101 невидим сегодня — две независимые причины

**Первая: комнаты вообще не цели мониторинга.** `collectTargets`
(`app/src/lib/monitor-targets.ts`) читает только `funnel_block_items`. Комнаты
живут в `funnel_days.gc_room/web_room/replay_url`:

```
gc_room    584 строки, все на gc.ksamata.ru
web_room   584 строки, все на web.ksamatacenter.com
replay_url  48 строк,  все на gc.ksamata.ru
gc есть / web пуст     0
web есть / gc пуст     0
```

Пары полные, перекосов нет. Целей из них не заведено ни одной.

**Вторая: проверка по коду ответа про них соврала бы.**

```
web.ksamatacenter.com/room/boo1-kvch    200, 27250 байт, <title>БЕЗОПАСНОЕ ОЧИЩЕНИЕ…</title>
web.ksamatacenter.com/room/tkm1-15-rb   200,  2388 байт, <title>Веб-комната не найдена</title>   ← F101
web.ksamatacenter.com/room/zzz-nope     200,  2388 байт, <title>Веб-комната не найдена</title>   ← контроль
gc.ksamata.ru/tkm1-15-rb                200, 58696 байт  ← страница ГК живая, комната за ней мёртвая
gc.ksamata.ru/zzz-nope-404              404
```

Страница комнаты F101 **побайтово того же размера**, что и заведомо выдуманный
слаг. `checkUrl` рвёт тело (`res.body?.cancel()`), поэтому цель встала бы в
«Работает».

Положительного признака «комната жива» не нашлось: из проверенных маркеров
`bizon` есть на обеих страницах, а `player`, `webinar`, `iframe` — ни на одной.
Различает их только `<title>`.

### Объём

Охват, выбранный владельцем (блоки `landings`, `tariffs`, `applications`,
`upsell` + три вида комнат):

```
уникальных адресов у активных воронок      1389   (сейчас включено 117)
у воронок всех статусов                    1767
в среднем на воронку                          24
максимум на воронку                           49
активных воронок без единого адреса            0
пересечение «адрес и комната, и пункт блока»   0
активных с rooms_enabled = 0, но со строками комнат   0
```

Полный цикл при `CONCURRENCY = 8` — около 3 минут против нынешних секунд, при
интервале 15 минут. Проверка одной воронки — от 3 секунд (всё живо) до ~2,5
минут (всё мёртвое: таймаут 10 с + пауза 3 с + ретрай 10 с на цель).

### Схема

`CHECK`-ограничений на `monitor_targets.source_kind` и
`monitor_source_kind_prefs.source_kind` нет. Миграция не нужна.

## Решения владельца, принятые в диалоге

| вопрос | решение |
|---|---|
| смысл пилюли | и индикатор состояния, и запуск проверки |
| охват | комнаты + лендинги + тарифы + заявки + допродажи; «Ссылки» и «Процессы» — по решению человека |
| черновики | фоновый цикл не трогает; ручная проверка работает у всех |
| повод зажечься | «Упало» и «не проверялось», раздельно; «Медленно» молчит |
| где детали | секция на карточке воронки |
| канарейка | делаем сразу |
| чип «Только с проблемами» | нужен |
| действие в списке | пункт «Проверить ссылки» в меню «⋮», без второй кнопки в строке |

## 1. Комнаты как цели мониторинга

`collectTargets` читает второй источник — `funnel_days` — наряду с
`funnel_block_items`. Три новых вида источника:

| вид | колонка | подпись группы |
|---|---|---|
| `room_gc` | `funnel_days.gc_room` | Комнаты ГК |
| `room_web` | `funnel_days.web_room` | Комнаты Web |
| `room_replay` | `funnel_days.replay_url` | Повторы |

Три, а не один: это три разных хоста и три разные причины падения, и только у
`room_web` нужна проверка по содержимому. Слитая группа не выключалась бы по
частям.

**Реестр видов.** `sourceKindLabel`/`isKnownSourceKind`
(`app/src/lib/monitor-kinds.ts`) сегодня выводятся из `BLOCK_KINDS` — «каждая
проверяемая страница приходит из блока». Это перестаёт быть правдой, поэтому
заводится явный `MONITOR_SOURCE_KINDS = BLOCK_KINDS ∪ ROOM_KINDS`. Правило из
того же файла остаётся в силе: незнакомый вид можно **читать**, но нельзя
**записывать** в `monitor_source_kind_prefs` — таблица вечная, опечатка осела
бы в ней навсегда.

**Дефолт групп.** `groupDefault` возвращает «да» для набора
`{landings, tariffs, applications, upsell, room_gc, room_web, room_replay}`
вместо одного `landings`. Строки `monitor_source_kind_prefs` по-прежнему
главнее дефолта, поэтому группа, выключенная человеком, останется выключенной,
а у целей с `manual_override = 0` синк пересчитает `enabled` сам.

**Границы сбора:**

- воронка с `rooms_enabled = 0` комнат не отдаёт, с `rooms_replay_enabled = 0`
  — повторов. Это решение человека «здесь нет эфиров», и его уже уважают
  карточка, компактный вид и `buildExportRows`; мониторинг обязан читать данные
  так же. Замер: таких активных воронок сейчас ноль — правило заведено на
  будущее и ничего не стоит;
- `sourceRank` не меняется («лендинг главнее, прочее вровень»): пересечение
  комнат и пунктов блоков — 0 адресов, правило чисто страховочное.

## 2. «Страница есть, а комнаты нет»

Новый чистый модуль `app/src/lib/monitor-content.ts` — ни сети, ни БД, ни
`node:*`:

```ts
export const SOFT_MISSING: Record<string, { re: RegExp; reason: string }> = {
  'web.ksamatacenter.com': {
    re: /<title>\s*Веб-комната не найдена\s*<\/title>/i,
    reason: 'Веб-комната не найдена',
  },
};
export function softMissingReason(hostname: string, head: string): string | null
```

`checkUrl` меняется в одном месте: если хост финального ответа есть в таблице и
ответ 2xx — прочитать **не более 8 КБ** тела и проверить признак; иначе рвать
тело, как сейчас. Совпало — `status: 'down'`, `httpStatus: 200`,
`error: 'Веб-комната не найдена'`. Для всех прочих хостов не меняется ничего.

8 КБ хватает с запасом: `<title>` лежит в `<head>`, а вся страница-пустышка —
2,4 КБ. Матчим по `<title>`, а не по вхождению строки в тело: живая комната
может законно содержать такие слова в чате или в названии вебинара.

`room_gc` по содержимому не проверяем: gc-страница F101 полноценная (58 КБ,
свой заголовок), она лишь встраивает мёртвую комнату. Раз пары `gc`/`web` в
базе полные (584 и 584), достаточно `room_web`.

### Канарейка

Отрицательный признак протухнет, если Bizon поменяет формулировку, и тогда все
комнаты станут «Работает» — то есть отказ прочтётся как «расхождений нет». Это
ровно тот тихий ноль, на котором репозиторий уже обжигался дважды (написание
тега `Предписок`, Phase 15; классы аудита под `--no-api`).

Поэтому заводится канарейка — заведомо несуществующий слаг
`web.ksamatacenter.com/room/ksamata-funnels-canary` (такой не будет создан
никогда). Не опознался как пропавший — признак протух.

**Считает её чтение, а не цикл.** Положить результат в `globalThis` из цикла
нельзя: цикл живёт в рантайме инструментации, страница рендерится в Node,
общего `globalThis` у них нет — ровно та причина, по которой `monitor-view.ts`
отказывается показывать ошибки отправки в Telegram. Такой флаг врал бы. Класть
в базу — значит заводить таблицу ради одного булева значения.

Поэтому канарейку дёргает роут `GET /api/monitoring` — тот же рантайм, что и
страница, — с кэшем на `CANARY_TTL_MS = 10 минут` на `globalThis`. Кэш
обязателен: пока идёт цикл, страница опрашивает роут раз в 2 секунды. Смотрят
на этот флаг ровно тогда, когда открывают мониторинг, то есть проверка
происходит там же, где её читают.

Состояний три, и третье — не придирка: сетевой сбой тоже даёт `down`, и выдать
его за «признак цел» нельзя.

| ответ на канарейку | состояние | что в шапке |
|---|---|---|
| `down`, `error` равен `reason` правила | `ok` | «Проверка комнат: действует» |
| 2xx без признака | `broken` | «Проверка комнат: не действует» (предупреждение) |
| всё прочее (сеть, таймаут, 5xx) | `unknown` | «Проверка комнат: не удалось проверить» |

Канарейка **не цель мониторинга**: иначе вечное «Упало» в дашборде, в
счётчиках групп и в Telegram. Она не попадает ни в `monitor_targets`, ни в
`monitor_state`, и отдельным ключом `roomCheck` лежит в ответе
`GET /api/monitoring`, рядом с `summary`, а не внутри него — `getMonitorDashboard`
остаётся синхронной.

## 3. Состояние воронки: агрегат и доступ

Новый модуль `app/src/lib/monitor-funnel-health.ts` — только чтение:

```ts
interface FunnelHealth {
  down: number;              // целей «Упало», включая «комната не найдена»
  unknown: number;           // заведены, но ни разу не проверялись
  enabled: number;           // адресов воронки под постоянной проверкой
  total: number;             // адресов у неё всего
  lastCheckedAt: string | null;
}
export function getFunnelHealth(db: AnyDB, funnelIds?: number[]): Map<number, FunnelHealth>
export function funnelHealthTone(h: FunnelHealth): 'down' | 'unknown' | 'ok'
```

Один запрос на весь список: `monitor_target_funnels` → `monitor_targets` →
`monitor_state`, группировка по воронке. `down` бьёт `unknown`.

`total` нужен не для красоты: без него карточка не скажет «12 адресов из 30 вне
проверки», и молчание пилюли у воронки с выключенными «Ссылками» читалось бы
как «всё живо».

**Точные правила:**

- `down` — любая связанная цель в статусе `down`, включённая или нет, с
  проверкой не старше `STALE_AFTER_DAYS = 7`. Выключенность не делает падение
  неправдой: человек сам попросил проверить. Отсечка по свежести и даёт тишину
  у архива: его страницы мертвы законно, и это как раз значит «архив»;
- `unknown` — связанная и **включённая** цель, которую не проверяли ни разу.
  Выключенная непроверенная пробелом не считается: её никто и не обещал
  проверять, иначе у каждого архива висела бы серая пилюля.

**Доставка — отдельным роутом `GET /api/monitoring/funnels`**, не полем в
`/api/funnels`: последний лежит в белом списке публичного чтения
(`app/src/lib/auth.ts`), и состояние мониторинга стало бы публичным. Новый роут
закрыт `requireEditor`, в белый список не попадает, и список зовёт его только
при `useCanEdit()`. Побочно это не тормозит первую отрисовку списка.

**Видно только редактору.** `/monitoring` уже за `EditorGate`; показывать
анониму то, чего он не может ни открыть, ни перепроверить, незачем.

### Смена смысла `monitor_target_funnels`

Единственный ломаемый инвариант, и он нужен для решения «черновики — по
кнопке». Сегодня связи хранятся только для **активных** воронок, а синк
отвязывает всё прочее. Ручная проверка черновика записала бы результат, а
ближайший фоновый прогон (≤ 15 минут) снял бы связь — пилюля погасла бы сама,
без объяснения.

Новый смысл: **`monitor_target_funnels` = «кто держит этот адрес», любого
статуса; проверяем ли — говорит `enabled`.** В синке это два раздельных правила
вместо одного:

- цели и связи собираются по всем статусам;
- `enabled` = дефолт группы **и** адрес держит хотя бы одна активная воронка;
- отвязывается только адрес, которого нет уже ни у кого.

Следствия:

- **дашборд упрощается.** `usage` (`active`/`inactive`/`orphan`) сейчас
  вычисляется пересборкой URL неактивных воронок через `collectFunnelUrls` —
  обходной путь именно потому, что связи были активными. Теперь статус читается
  прямо из связанных воронок, и у `collectFunnelUrls` пропадает вторая работа;
- **счётчики групп не меняются по смыслу:** «страницы активных воронок»
  становится «связана хотя бы с одной активной» — то же множество;
- **авто-ретайрмент честнее:** адрес, оставшийся у архива, гаснет, но связь
  сохраняет, и дашборд может объяснить, чей он;
- **цена — 378 дополнительных строк** `monitor_targets` (1767 против 1389), все
  погашенные, ни одной лишней проверки за цикл.

Правило «мониторим только активные» не отменяется: оно переезжает с места сбора
на место включения, туда, где и было его настоящее содержание.

## 4. Ручная проверка одной воронки

**Роут** `POST /api/monitoring/funnels/[id]/run` — под `/api/monitoring`, чтобы
подсистема жила в одном месте и не соседствовала с путями белого списка.
`requireEditor` первой строкой. Ответ **202**, как у общего прогона: 24 адреса
в среднем, 49 максимум, то есть от 3 секунд до ~2,5 минут.

**Сначала синк, потом проверка.** Перед прогоном цели этой воронки
пересобираются (`syncFunnelTargets(db, funnelId)` — тот же сбор, сужённый до
одной воронки). Иначе «поправил адрес → нажал проверить» проверяло бы старый
адрес.

**Проверяются все адреса воронки, включая выключенные.** Иначе кнопка
бесполезна там, где нужна больше всего: у черновика все цели выключены по
построению, и проверка отчиталась бы об успехе, не проверив ничего.

**Одновременность.** У проверки воронки **свой флаг** `funnelCheckRunning`,
тоже на `globalThis` (модули в прод-бандле раздваиваются — см. CLAUDE.md). Одна
проверка воронки за раз, параллельно общему циклу. Общий цикл теперь идёт ~3
минуты из каждых 15, и единый флаг давал бы отказ на каждом пятом клике по
главной кнопке.

Гонка за одну цель закрывается по-настоящему: в `persist`
(`app/src/lib/monitor-run.ts`) чтение прошлого статуса стоит **снаружи**
транзакции, а запись внутри. `SELECT` переносится внутрь — SQLite сериализует
пишущие транзакции, и «прочитали оба, записали оба» становится невозможным.
Сегодня это не стреляет лишь потому, что два писателя не могут наложиться;
снимая запрет, чинить надо причину.

**Опрос.** Карточка и список опрашивают `GET /api/monitoring/funnels` (и
`…/funnels/[id]` для подробностей); в ответе `checking: boolean` — идёт ли
проверка именно этой воронки. Период опроса и предел неудач берутся те же, что
на `/monitoring` (`POLL_INTERVAL_MS`, `MAX_POLL_FAILURES`): два разных периода
в одном сервисе разъедутся.

## 5. Интерфейс

### Пилюля в списке

Компонент `FunnelHealthPill` встаёт в `FunnelCard` **внутрь той же
flex-группы**, где уже живут `StatusPill` и чип типа воронки. Не отдельной
колонкой сетки: пилюля есть у меньшинства строк, и фиксированная колонка
оставила бы дыру у остальных — карточка уже разъезжалась из-за жёсткой второй
колонки.

| условие | вид | подсказка |
|---|---|---|
| `down > 0` | красная «Проверить · N» | «N адресов не отвечают» |
| `down = 0`, `unknown > 0` | серая «Не проверялось» | «Адреса ещё ни разу не проверяли» |
| иначе | ничего | — |

Видна только редактору. Клик ведёт на карточку, на якорь секции.

**Действие без ухода со списка** — пункт «Проверить ссылки» в меню «⋮» строки.
Второй кнопки в строке не добавляем.

**Порядок списка не меняется.** На образце (интерфейс ЛИК) проблемные воронки
подняты наверх; у нас порядок — `compareByFrontCodeDesc`, зафиксированный
инвариант. Вместо пересортировки — чип-переключатель **«Только с проблемами»**
рядом с `FacetBar`, выключенный по умолчанию. Перемешивать порядок молча
нельзя: человек ищет F101 там, где тот всегда стоял.

### Секция «Проверка ссылок» на карточке

Отдельный компонент, встаёт в `FunnelSections` **последним** — после блоков и
сетки комнат: читают её после того, как что-то заподозрили. Содержимое:

- шапка: состояние, «проверено N минут назад», кнопка «Проверить сейчас» с
  прогрессом по `checking`;
- список проблемных адресов: адрес, **откуда он** («Комната ГК · 15:00 ·
  день 2», «Тарифы · Основной»), что не так («HTTP 404», «Веб-комната не
  найдена», «Таймаут 10 с»), с какого времени лежит (`since`);
- строка «N адресов из M вне постоянной проверки» со ссылкой на `/monitoring`.
  Без неё молчание секции у воронки с выключенными «Ссылками» читалось бы как
  «всё живо».

**Происхождение адреса новой колонки не требует:** для одной воронки её адреса
пересобираются при чтении (тот же сбор, что в синке) и сшиваются с целями по
нормализованному URL. Колонка `origin` в `monitor_targets` была бы неверна по
существу — один адрес может принадлежать двум воронкам с разным
происхождением.

**Анониму секции нет вовсе** — не `readOnly`, а нет: роут ответит ему 401, и
пустая секция выглядела бы поломкой.

## Чего не делаем

- **Не заводим таблиц и колонок.** Ни фазы в цепочке `docker-entrypoint.sh`, ни
  DDL: `CHECK` на `source_kind` нет, новые виды ложатся в существующий `TEXT`,
  новый смысл связей синк приводит сам на первом же прогоне. Откат — откат кода.
- **Не троттлим по хосту.** ~600 запросов за цикл на `gc.ksamata.ru`, но при
  `CONCURRENCY = 8` одновременных не больше восьми. Это обычный веб-трафик, а
  не legacy API GetCourse с его лимитами. Ручки `CONCURRENCY` и
  `MONITOR_INTERVAL_MINUTES` остаются.
- **Не проверяем `room_gc` по содержимому** — см. раздел 2.
- **Не зажигаем пилюлю по «Медленно».** Страницы ГК регулярно тормозят без
  повода; пилюля стала бы фоном.
- **Не пересортировываем список.**

## Тесты

Vitest, русские имена, временная копия базы через `copyDbForTest`, обязательный
`clearMonitoringState` сразу после миграций — как во всех монитор-тестах.

- комнаты попадают в цели; `rooms_enabled = 0` — не попадает; связи заводятся
  у всех статусов, `enabled` — только у активных; отвязывается только ничей
  адрес;
- признак «комнаты нет» совпадает на сохранённом образце страницы-пустышки и
  **не** совпадает на образце живой комнаты (два фикстура, обрезанные до
  `<head>`);
- тело читается только для хостов из таблицы и не больше 8 КБ; 200 + признак →
  `down`; 200 без признака → `up`;
- канарейка: ответ без признака даёт `broken`, сетевой сбой — `unknown`, а не
  `ok`; кэш не даёт второму вызову подряд уйти в сеть;
- агрегат: `down` бьёт `unknown`; выключенная непроверенная цель `unknown` не
  даёт; падение старше 7 дней пилюлю не зажигает;
- два флага не мешают друг другу; `persist` читает и пишет в одной транзакции;
- роуты: аноним 401, 202 на старт, 409 на повтор, синк перед прогоном.

## Риски

1. **Первый прогон даст лавину.** Включённых целей станет 1389 вместо 117, и
   разом обнаружится всё, что молча лежало годами, включая законно мёртвые
   страницы архива. В Telegram это уйдёт одним сообщением (`MAX_LINES_PER_SECTION`
   и `MAX_MESSAGE_CHARS` на месте), но число в заголовке будет трёхзначным. Это
   правда, а не сбой. **Выкатывать при `MONITOR_ENABLED=false`**, прогнать цикл
   вручную, разобрать, потом включать фон.
2. **Признак «комнаты нет» протухнет.** Закрывается канарейкой: протухание
   становится громким, а не тихим.
3. **Нагрузка на `gc.ksamata.ru`** — см. «Чего не делаем».
4. **Edge-сборка.** `monitor-content.ts` обязан остаться чистым. Любой
   Node-импорт под `monitor-*.ts` валит `npm run build`, оставляя `tsc` и тесты
   зелёными (`app/next.config.ts`). Проверка — именно `npm run build`.

## Порядок работ

1. `monitor-content` + `monitor-canary` + чтение тела в `checkUrl` + флаг в шапке.
2. Комнаты как источник целей, реестр видов, новые дефолты групп.
3. Смена смысла `monitor_target_funnels` + упрощение `usage` в `monitor-view`.
4. Агрегат `monitor-funnel-health` + `GET /api/monitoring/funnels`.
5. Ручная проверка воронки: `POST …/run`, второй флаг, `SELECT` внутрь
   транзакции в `persist`.
6. Интерфейс: пилюля, чип «Только с проблемами», пункт «⋮», секция на карточке.

Каждый шаг самодостаточен и проверяем отдельно.

## Проверка готовности

`npx tsc --noEmit`, `npx vitest run`, `npm run build` из `app/`, затем живой
прогон на копии базы через `FUNNELS_DB_PATH` — и глазами на `/monitoring` и на
карточке **F101**: она и есть эталонный случай.

Фича не меняет ни одной строки данных воронок, поэтому сид и `seed-parity` не
затрагиваются. Но ручные прогоны пишут в `monitor_*` отслеживаемого файла —
после любой живой проверки базу восстанавливать по рецепту из CLAUDE.md и
убеждаться, что `monitor_targets` снова ноль.
