# Карта расхождений тегов воронок

> Дата: 2026-07-24
> Статус: реализовано, ветка docs/funnel-tag-drift-map
> Область: проект **A** из трёх (см. «Декомпозиция»)

## Цель

Построить **карту расхождений** между тремя источниками правды о тегах воронок:
реестром предложений в GetCourse, историей выгрузок заказов и локальной базой
`ksamata_funnels.db`.

**Эталона нет.** Ни один источник не объявляется правильным. Задача — увидеть
полную картину «где что не сходится» и дать человеку основу для решений.
Скрипт ничего не чинит автоматически: ни базу, ни GetCourse.

## Декомпозиция

Исходная задача «проверить все воронки» распадается на три независимых проекта
с разной ценой и разными доступами:

| | Что | Чем делается | Доступы |
|---|---|---|---|
| **A** | Карта расхождений по тегам | детерминированный скрипт | API GetCourse (чтение), локальные файлы |
| **B** | Аудит дашбордов | агенты в браузере | GetCourse UI |
| **C** | Аудит регистраций | тестовые прогоны + агент | GetCourse, лендинги, боты |

**Этот спек покрывает только A.** B и C берутся отдельными циклами после того,
как карта построена: без списка тегов для сверки агент проверяет интерфейсы
вслепую. Побочный результат A — список воронок без расхождений, чьи дашборды
можно смотреть в последнюю очередь.

## Источники

### 1. API GetCourse — текущее состояние, авторитетно

```
GET /pl/api/v1/offer/get-offers        → Offer { id, title, code, price, status, params }
GET /pl/api/v1/offer/get-offers-tags   → OfferTag { offerId, tags: string[] }
```

Авторизация: заголовок `Authorization: Bearer <devKey>_<apiKey>`,
базовый URL `https://<domain>/pl/api/v1`. Параметр `page` молча игнорируется
и возвращает первую страницу снова и снова — пагинация ожидалась через
`limit`/`offset`, но на практике оказалась **асимметричной между двумя
эндпоинтами** этого источника:

- `offer/get-offers-tags` честно уважает `limit`/`offset` — постраничный
  обход через них работает как ожидалось.
- `offer/get-offers` **игнорирует оба параметра** и всегда отдаёт весь
  реестр целиком одним ответом, вне зависимости от `limit`/`offset`.
  Прогнать его через постраничный `fetch_all()` нельзя: каждая «страница»
  оказывается больше `page_size`, цикл решает, что данные не кончились, и
  уходит в бесконечную пагинацию до предохранителя (`MAX_PAGES`) — на живом
  прогоне это не уложилось в 10 минут и разорвало соединение. Это
  заблуждение (что оба эндпоинта пагинируют одинаково) стоило проекту
  критического бага именно такого рода; `load_offers()` поэтому тянет
  `offer/get-offers` ОДНИМ запросом через `fetch_page()`, а
  `offer/get-offers-tags` — через честный постраничный `fetch_all()`.

Проверено на живых данных 2026-07-24: 7679 предложений, из них 2279 с АВ-тегами;
`offer/get-offers` отдаёт их одним ответом, `offer/get-offers-tags` —
постранично (в 8 запросов по 1000).

Единственный источник, который видит **предложения без единого заказа** — через
выгрузки заказов они невидимы в принципе.

**Поле `status` непригодно:** у всех 7679 предложений оно равно `draft`.
Признак «актуально / архивное» из API не выводится; актуальность оценивается
только по наличию заказов (класс 14).

### 2. Выгрузки `deal_export` — история и использование

Файлы `~/Downloads/deal_export_2026-04-*` … по текущую дату, `.xlsx` и `.csv`.

Фильтр отбора: наличие колонки **«Теги предложений»**. Файлы вида `*_utm.xlsx`
(13 колонок) отбрасываются — там её нет.

Ключевое свойство, **проверено на данных**: «Теги предложений» вычисляются
в момент выгрузки, а не хранятся на заказе. Одни и те же заказы, выгруженные
11 марта и 13 мая, дают разные наборы тегов (106 из 272 пересекающихся
изменились — добавился тег `СВС`).

Из этого следуют два обязательных требования:

- **Дрейф меряется по дате файла выгрузки, а не по дате создания заказа.**
  Привязка к дате заказа даёт ложную картину: мартовский заказ в майской
  выгрузке несёт майские теги.
- **Каждое наблюдение хранит обе даты** — дату файла (когда теги были такими)
  и дату заказа (к какому периоду относится сам заказ).

Второе ключевое свойство: **выгрузки — это сегментные срезы, а не единый
поток.** Проверено: файлы с перекрывающимися периодами дают ноль общих заказов,
потому что делались под разные вопросы. Покрытие по воронкам неравномерное и
заранее неизвестное — отсюда обязательный класс 16.

### 3. `ksamata_funnels.db` — ожидания

Открывается **только на чтение** (`file:...?mode=ro`). Скрипт не пишет в базу
ни при каких условиях.

Читаются `funnels`, `funnel_tags`, `tags`. Ожидаемый набор тегов — это
`funnel_tags` для пары (воронка, `tag_type`), то есть материализованный
результат «шаблон + оверрайды». Raw-строки `*_raw` не используются: они
импортно-экспортные артефакты.

## Ключ склейки

Имя предложения **не годится**: на одной выгрузке 26 уникальных «Составов
заказа» дали 11 имён с разными наборами тегов (до 6 вариантов на имя) — под
каждую воронку заведено своё предложение с тем же названием.

Ключ — **АВ-четвёрка**: `АВ Продукт` + `АВ Подрядчик` + `АВ Канал` +
`АВ Направление`.

Проверено со стороны базы: 49 уникальных ключей на 51 воронку, все 200 пар
(воронка × тип) имеют полную четвёрку. Со стороны GetCourse: 119 уникальных
полных четвёрок, 23 предложения с неполной.

Тип тега выводится из этапа и времени:

| Наблюдаемые теги | `tag_type` |
|---|---|
| `АВ Этап: Регистрация` | `reg` |
| `АВ Этап: Мессенджер` | `messenger` |
| `АВ Этап: Оплата` + `АВ Время: 19` | `time_19` |
| `АВ Этап: Оплата` + `АВ Время: 15` | `time_15` |
| `АВ Этап: Оплата` без `АВ Время` | — (класс 5) |
| `АВ Этап: Предписок` | — (классы 3 и 6) |

**Коллизии не разрешаются угадыванием.** Известная коллизия
`ЖИВО / НИМБ / Яндекс / РСЯ` указывает и на `f33` (ЖИВО НИМБ РСЯ), и на `f43`
(КВИЗЫ ЖИВО НИМБ) — у квиз-воронки направление размечено как РСЯ, а не Квиз.
Такая группа помечается `ambiguous` и уходит в отчёт как отдельная находка
(класс 8), а не приписывается одной из воронок.

## Единица наблюдения

Не заказ, а **наблюдаемый набор тегов**:

```
(id заказа, набор тегов, дата файла выгрузки, дата создания заказа)
```

Дедупликация — по паре `(id заказа, дата файла)`, а не по одному id заказа:
один и тот же заказ в двух выгрузках это два разных наблюдения, и именно их
расхождение и есть сигнал дрейфа.

Агрегат для отчёта — тройка `(воронка × tag_type × набор тегов)` с полями:
число заказов, `first_seen`, `last_seen` (обе — по датам файлов), список
файлов-источников.

**Текущее состояние воронки** берётся из API, а не из выгрузок. Выгрузки дают
историю и счётчики заказов.

Статус заказа (`Оплачен` / `Отменен` / …) игнорируется: теги предложения от
отмены заказа не меняются.

## Нормализация

- Trim, схлопывание внутренних пробелов, нормализация Unicode в NFC.
- Регистр приводится **только для сравнения**; в отчёт выводится оригинальное
  написание.
- Порядок тегов не значим — сравниваются множества.
- Синонимы **не** схлопываются автоматически. Решение, считать ли `автоворонки`
  и `АВ Автоворонка` одним и тем же, принимает человек; задача скрипта —
  показать, что они расходятся. Аналогично `АВ Этап: Предписок` и легаси-тег
  `предсписок` — разные написания одного понятия, сводить их вправе только
  человек.

## Классы находок

Каждый класс — отдельный лист отчёта, а не общая свалка. В скобках — числа,
уже подтверждённые на разведке 2026-07-24.

**Группа I. Расхождения в наборах тегов (база ↔ GetCourse)**

1. Тег ожидается в базе, но в GetCourse почти отсутствует —
   `автоворонки` ожидается на всех 200 парах, реально стоит на 312 из 8124
   предложений в выгрузке.
2. Ось живёт в GetCourse, но её нет в словаре базы —
   `АВ / Мессенджер`, `АВ Мессенджер: МАКС|ВК` (3151 заказ в одной выгрузке).
3. Этап есть в GetCourse, но не поддержан моделью базы —
   `АВ Этап: Предписок` (233 заказа за 5 дней), при том что
   `funnel_tags.tag_type` разрешает только `reg / time_19 / time_15 / messenger`
   и ни у одной воронки не заполнен `predspisok_url` (0 из 51).
4. Противоречивые легаси-теги на одном предложении —
   `ВК NR ВК` и `ВК NR IS` одновременно.

**Группа II. Сбои опознания (набор не удаётся привязать к воронке)**

Классы 5–7 взаимоисключающи: каждая неопознанная группа попадает ровно в один
из них. На разведке не опознана 31 группа из 94.

5. Оплата без `АВ Время` — тип не выводится (13 групп).
6. Этап `Предписок` — типа для него в модели базы нет (7 групп).
   Следствие класса 3, но учитывается отдельно, чтобы не смешивать
   «модель неполна» и «разметка сломана».
7. АВ-четвёрка полная и тип выведен, но воронки с такой четвёркой в базе нет
   (11 групп). Пересекается с классом 9 по смыслу, но считается по выгрузкам,
   а не по реестру API.

**Группа III. Полнота базы относительно реестра GetCourse**

8. Коллизия АВ-ключа — одна четвёрка указывает на две воронки (`f33` / `f43`).
9. АВ-четвёрка есть в GetCourse, но нет ни одной воронки в базе —
   119 четвёрок в GetCourse против 49 в базе, то есть около 70 неучтённых
   комбинаций. **Самый крупный класс.**
10. Предложение с неполной АВ-четвёркой (23).
11. Ось есть в GetCourse, но отсутствует в словаре базы целиком —
    `АВ Линейка` (26), `АВ Мессенджер` (133), `АВ / Мессенджер` (85),
    `АВ Прямые` (55), `АВ Квиз` (18), `АВ Квиз-Лайт` (12).
12. Предложение с `АВ Этап`, но без `АВ Автоворонка` (88).

**Группа IV. Актуальность**

Классы 13 и 14 смотрят с разных сторон и намеренно не сводятся: 13 — от базы
(воронка заведена, следов нет), 14 — от GetCourse (предложение существует,
заказов нет). Воронка может попасть в 13, а её предложения — в 14; это два
разных вывода для человека.

13. Воронка в базе `active`, но за период ни одного наблюдения — «мёртвая
    по данным».
14. Предложение с АВ-тегами и нулём заказов за период — кандидат в архив.
    Замена нерабочему полю `status`.

**Группа V. Динамика и достоверность**

15. Дрейф: когда тег появился у группы или исчез, с интервалом дат между
    соседними выгрузками, в которых группа наблюдалась.
16. Покрытие: по каждой воронке — сколько наблюдений, из скольких файлов,
    дата последнего. Воронка с одним апрельским наблюдением это не «всё
    хорошо», а «мы почти ничего не знаем». **Без этого листа отчёт врёт**,
    потому что выгрузки — сегментные срезы с неизвестным охватом.

## Выход

Один XLSX в `data/generated/` (каталог gitignored):

- **Сводка по воронкам** — строка на воронку: front_code, продукт, статус,
  число находок по каждому классу, дата последнего наблюдения, оценка покрытия.
- **Лист на каждый класс находок** — с колонкой `Решение`, пустой, под ручную
  простановку.
- **История дрейфа** — изменения наборов тегов с датами.
- **Покрытие** — класс 16 отдельно.
- **Источники** — какие файлы выгрузок обработаны, их даты, число строк;
  дата и объём снимка API.

Плюс сырой снимок ответа API рядом, в `data/generated/` — чтобы прогон был
воспроизводим без повторного обращения к GetCourse.

## Размещение и гигиена

Код: `tools/audit/`, Python — по конвенции репозитория (рядом с
`tools/data-import` и `tools/data-export`, пути резолвятся от корня репозитория,
запускается из любого рабочего каталога).

- Ключи GetCourse **не копируются** в этот репозиторий. Скрипт читает
  `GC_DEV_KEY`, `GC_API_KEY`, `GC_DOMAIN` из окружения. Ключи не попадают
  ни в логи, ни в отчёт, ни в сырой снимок.
- База открывается только на чтение. Файл `ksamata_funnels.db` после прогона
  обязан остаться неизменным (`git status --porcelain` чистый).
- Ни выгрузки, ни снимок API, ни отчёт в git не коммитятся.

## Вне охвата

- **Любая автоправка** базы или GetCourse. Выход — только отчёт.
- **Дашборды и регистрации** — проекты B и C.
- **Точная датировка дрейфа до дня.** Разрешение ограничено плотностью
  выгрузок: мы знаем только интервал между двумя соседними файлами, в которых
  группа наблюдалась.
- **Ретроспектива глубже апреля 2026.** Более ранние выгрузки существуют, но
  в охват не берутся.

## Открытые вопросы

Ни одного блокирующего. Все спорные места разрешены на разведке: ключ склейки,
модель истории и пригодность API проверены на живых данных до написания спека.
