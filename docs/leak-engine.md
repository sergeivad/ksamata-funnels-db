# LeakEngine — приёмник f-кодов воронок

**LeakEngine** (`https://leak.besales.ai`) — внешняя система атрибуции, экран
«Воронки / Правила» (`/funnels/rules`).

## Правило нумерации (действует с 2026-08-04)

**F-код назначает база. ЛИК его принимает.**

Порядок работы: новая воронка заводится **сначала в базе** и сразу получает
код — `max(front_code) + 1` по этой базе (`nextFrontCode`,
[app/src/lib/front-code.ts](../app/src/lib/front-code.ts)). Затем владелец
переносит воронку в ЛИК **под тем же кодом**.

Пустой код при заведении — больше не норма: он был обходом, пока эталон был
на той стороне.

Что не изменилось и меняться не должно:

- **`max + 1`, а не первая дыра.** Дыры (`f10`, `f14`, `f17`, `f18`, `f20`,
  `f44`, `f49`, …) — чужие номера, занятые в ЛИК раньше; переиспользовать их
  нельзя. Максимум считается по обеим сторонам: если в ЛИК код выше нашего
  (воронку завели там напрямую), берём выше него.
- **Код не выводится из `num`.** `num` — внутренний ключ, к нумерации F
  отношения не имеет. Именно так появились `f64`–`f72`: 2026-07-26 им
  проставили «следующие свободные» по `num`, и коды сели на чужие номера.
- **Уникальный индекс (Phase-7) не даёт завести две воронки с одним кодом**
  даже случайно.

Заведение воронки в админке подставляет код автоматически — теперь это не
подсказка, а рабочее значение; переопределять его нужно только если ЛИК уже
занял этот номер.

### Что было раньше

- **2026-07-19:** «воронки нет в ЛИК → код пустой». Осторожно, но воронки
  месяцами жили без кода.
- **2026-07-28:** «есть в ЛИК → берём оттуда; нет → `max + 1`». ЛИК считался
  источником истины, база подстраивалась.
- **2026-08-04:** источник истины — база. Причина простая: воронка появляется
  у нас раньше, чем в ЛИК, и ждать чужого номера означает держать её без кода
  ровно столько, сколько до неё не дойдут руки.

**Писать в ЛИК — только по прямой просьбе владельца** (см. «Как завести
воронку»): активация набора правил запускает пересчёт заявок.

**Воронки в ЛИК не выключаем — никогда** (решение 2026-08-04). Расхождение
«у нас `archive`, в ЛИК `ACTIVE`» расхождением не считается.

## Признак «есть в ЛИК» в базе

С 26.09.2026 у воронки есть `funnels.in_leak` (Phase 18): список показывает
пилюлю «ЛИК» или «нет в ЛИК». Синхронизации нет. Завели воронку в ЛИК, значит
ставите галку «есть в ЛИК» на её карточке. Первоначальное заполнение сделано по
снимку реестра от 26.09.2026 (`app/scripts/migrate-phase18-data.ts`).

С 30.09.2026 рядом лежит `funnels.leak_todo` (Phase 20): свободный текст «чего не
хватает в ЛИК». Воронку иногда заводят в ЛИК заранее, для планирования, и набор
правил получается неполным: нет предложения регистрации в GetCourse, нет
вебинарных комнат. Когда галка «есть в ЛИК» стоит и поле непустое, список
показывает пилюлю «ЛИК · доделать», а в подсказке к ней стоит этот текст. Поле
появляется на карточке под строкой идентификации только при поднятой галке.
Опустошили поле, значит воронка заведена полностью, пилюля снова «ЛИК». Без галки
поле на пилюлю не влияет. Фаза данных не засевает: недоделки называет человек.
Дубликат воронки поле не наследует.

## Как забрать список

Внутренний API отдаёт весь реестр одним запросом, но **только по сессионной
куке** — токена нет, поэтому запрос делается из вкладки уже залогиненного
браузера, через Chrome MCP (`mcp__claude-in-chrome__*`), не через `curl`.

1. Открыть вкладку: `navigate` → `https://leak.besales.ai/funnels/rules`
2. Выполнить в контексте страницы (`javascript_tool`):

```js
const r = await fetch('/app-api/api/admin/funnels', {credentials:'include'})
              .then(r => r.json());
r.funnels.map(f => [f.funnelCode, f.funnelName, f.productCode, f.status]);
```

Ответ — объект с ключом `funnels`. Поля, которые нужны на практике:

| Поле | Что это |
|---|---|
| `funnelCode` | `f6`, `f27`, … — то, что кладём в `front_code` |
| `funnelName` | у воронок начиная с `f27` это буквально АВ-четвёрка «Продукт / Подрядчик / Канал / Направление»; у `f6`–`f26` — легаси-описание |
| `productCode` | внутренний код продукта ЛИК (`boo`, `dbo`, `zkt`, `shzh`, …), с продуктами базы не совпадает |
| `status` | `ACTIVE` / `INACTIVE` / `DRAFT` |
| `rulesPacks[]` | наборы правил: в списке только шапка версии (`id`, `version`, `status`, `effectiveFrom`, `effectiveTo`, `activation`, `validation`), **без содержимого правил** (замер 30.09.2026) |
| `notes` | заметка к воронке, свободный текст из формы; удобно держать там «чего не хватает» |
| `advertisingSpendMode` | способ получения расходов: `AUTOMATED` / `MANUAL` / `NO_SPEND`, у всех воронок с f80 по f105 `AUTOMATED` |
| `advertisingExpectation`, `resolvedAdvertisingExpectation` | ожидание рекламных данных: `AUTO` у новых, `PAID` у старых; вычисленное значение у всех `PAID` |
| `readinessIssues[]` | что ЛИК сам считает недонастроенным, `{code, label}`; у f104 это `ADVERTISING_MAPPING_MISSING` «Не настроен рекламный мэппинг» |
| `funnelRole` | пока у всех `null` |

**Содержимое правил отдаёт только карточка:** `GET /app-api/api/admin/funnels/{id}`,
там у версии есть `registrationRuleJson`, `applicationRuleJson`,
`attendanceRuleJson`, `followUpRuleJson`, `attributionRuleJson`,
`stageMapJson`, `benchmarkRulesJson`, `ruleProvenanceJson`. Раньше эти поля
приходили и в списке; скрипт, читающий их из списка, теперь молча получит
`undefined` и решит, что правил нет. Число основных дней лежит внутри
`attendanceRuleJson` как `max_primary_webinar_day`, коды комнат там же в
`source_room_codes`.

Соседние эндпоинты той же админки: `/app-api/api/admin/products`,
`/app-api/api/auth/session`.

## Как завести воронку

Проверено 2026-08-02: так заведены `f73`, `f74`, `f78`. Всё — тем же
`fetch` из залогиненной вкладки, `credentials:'include'`.

Заведение — **два шага**: сама воронка и набор правил к ней. Воронка без
набора правил ничего не считает.

### 1. Воронка

```js
POST /app-api/api/admin/funnels
{ "funnelCode": "f78", "funnelName": "ТКМ / NR / ВК / Реклама",
  "productCode": "tkm", "businessTimezone": "Europe/Moscow", "status": "DRAFT" }
```

`productCode` берётся из `/app-api/api/admin/products` и с продуктами базы не
совпадает: ТКМ там `tkm` с отображаемым именем «КОД МОЛОДОСТИ», ЖИВО — `jivo`
на всю линейку (`ЖИВО-суставы`, `ЖИВО-ЖКТ`, `ЖИВО-суставы-триал` — один
`productCode`, различает их только `АВ Продукт` в метках).

### 2. Набор правил

```js
POST /app-api/api/admin/funnels/{funnelId}/rules-packs/save-and-activate
```

Тело — **поля формы, а не сырой rule-JSON**: сервер сам собирает из них
`registrationRuleJson`, `applicationRuleJson`, `attendanceRuleJson`,
`stageMapJson` и прочее. Руками эти блобы писать не надо.

| Поле | Значение |
|---|---|
| `templateKey` | `webinar_multi_day` — единственный используемый |
| `effectiveFrom` | `ГГГГ-ММ-ДД`, обязательное. **С этой даты ЛИК пересчитает заявки** |
| `effectiveTo` | можно не слать |
| `registrationOfferNames` | названия предложений регистрации; у «Прямых» — `[]` |
| `applicationTags` | АВ-набор этапа «Оплата»: маркер типа + `АВ Этап: Оплата` + четыре оси |
| `webinarRoomCodes` | коды комнат; у «Прямых» — `[]` |
| `maxPrimaryWebinarDay` | 5 у пятидневных, 3 у трёхдневных и у «Прямых» |
| `prelistApplicable` | `true`, если у воронки поднят `funnels.has_predspisok` (в форме — галочка «Учитывать предсписок»), иначе `false`. Прежнее «`false` у всех» неверно — замер 11.09.2026. Набор меток и разбор — раздел 2а |
| `paymentLinkRule` | `payments.Заказ = deals.Номер` |
| `paymentSuccessStatuses` | `["Получен","Списание с баланса"]` |
| `paymentExcludedStatuses` | `["Ожидается","Возвращен","Начислен на депозит"]` |
| `paymentBridgeAllowedExcludedApplicationOrderTags` | `["дубль"]` |
| `applicationExcludedTags` | `["дубль","тест"]` |
| `applicationExcludedStatuses` | `[]` |
| `firstPayExcludedTags` | `["дубль","тест","2-й платеж","3-й платеж","полная оплата"]` |
| `cashRevenueExcludedTags` | `["дубль","тест"]` |
| `analysisHorizon` | `live_operational` |

Всё, кроме первых шести строк, у всех воронок ЛИК одинаково — форма
подставляет эти значения сама, и отличаться там ничего не должно.

### 2а. Предсписок

В форме это галочка **«Учитывать предсписок»** и появляющееся под ней поле
**«Метки предложений предсписка»**. Оседает в `followUpRuleJson`:

```json
"prelist_applicable": true,
"prelist_order_rule": {
  "match_mode": "ALL",
  "source_entity": "deals",
  "source_system": "GETCOURSE",
  "schema_version": 1,
  "offer_tags_field": "Теги предложений",
  "required_offer_tags": [ … шесть меток … ]
}
```

`match_mode: ALL` — то же **И**, что и в `applicationRuleJson.exact_tag_filters`:
подпись под полем гласит, что заказ относится к предсписку, только если у его
предложения есть **все** указанные метки. Лишние метки на предложении не мешают,
недостающая обнуляет фильтр целиком.

Набор — тот же, что у оплаты, только этап другой: маркер типа + четыре оси
воронки + `АВ Этап: Предсписок`. Замер 01.09.2026 по реестру GetCourse: у всех
34 предложений предсписка эта шестёрка полная, а пятёрка «оси + маркер»
уникальна — на воронку ровно одно предложение.

**Этап пишется `АВ Этап: Предсписок`, через «с».** Раньше в реестре стояло
`Предписок` без «с», и это было записано у нас как опечатка GetCourse, которую
обязательно повторять. Между 30.07 и 01.09.2026 GetCourse её исправил: старого
написания не осталось ни на одном из 7901 предложения (было 14), новое стоит на
34. Те же id живы — сменился только тег. Фильтр сравнивает дословно, поэтому
воронки, которым предсписок проставили 25.08 со старым написанием, не ловили
ни одного заказа, и выглядело это как «настроено».

Состояние на 01.09.2026: предсписок включён у **32** воронок — всех, у кого в
GetCourse есть предложение этапа и кто заведён в ЛИК. `f64` и `f97` в ЛИК нет.

**Обновление 11.09.2026:** `f97` и `f98` заведены в ЛИК, у обеих предсписок
включён — `prelist_applicable: true` и полная шестёрка меток. Общее число
заново не считали, счёт выше остаётся замером на 01.09. Из названных выше в
ЛИК по-прежнему нет `f64` — она архивная, и заводить её не решили.

### 3. Активация воронки

```js
PATCH /app-api/api/admin/funnels/{funnelId}   { "status": "ACTIVE" }
```

Без подтверждения и без пересчёта.

### ⚠️ Заводить — кликами в интерфейсе, а не этим API

Вендор 2026-08-24: «АПИ открытое мы пока не делали, а закрытое лучше пока не
юзать, так как могут быть корнер кейсы, где используются какие-то операции на
фронте». Описание запросов выше остаётся как справка о контракте — **делать
надо формой**. Проверено на f96 (28.08): форма «Новая воронка» и панель
«Настройка набора правил» заполняются агентом целиком, и собранный ими
`attendanceRuleJson` вышел полным (13 043 знака), тогда как у f66, заведённой
тем же телом через API, — 165 знаков. То есть корнер-кейс не гипотетический.

Как работать с формой:

- Строки реестра и все выпадающие списки — `<button>`, а не `<select>`.
  Действовать по `ref` из `read_page`/`find`: координаты скриншота и вьюпорта
  расходятся примерно на 4 %, и клик по пикселям уезжает мимо панели, закрывая
  её вместе с введёнными данными.
- В списочные поля (предложения, метки, коды комнат) значение добавляется
  вводом и **Enter**.
- **Кнопка «Активировать воронку» остаётся `disabled`, пока страницу не
  перезагрузить** после того, как набор правил стал ACTIVE. Список держит
  состояние, снятое до активации, и сам не обновляется.

**Дату `effectiveFrom` всё равно спрашивать у владельца** — она задаёт окно
пересчёта.

**Нативный `confirm()` при активации есть — но не у всякой воронки.** Замер
28.08: у выключенной (`f16`) сохранение прошло сразу тостом «Правила сохранены.
Проверка и активация выполняются в фоне», диалога не было вовсе. У активной
(`f43`, два сохранения подряд) он вылезал оба раза, морозил вкладку, и клик
`Input.dispatchMouseEvent` отваливался по таймауту 30 с. **Таймаут здесь не
провал**: сохранение уже ушло, и после разморозки кнопка стоит в «Проверка и
активация выполняются…». Повторять клик нельзя — создастся лишняя версия.

> **Поправка 2026-09-11: диалог есть и у совсем новой воронки, и там таймаут
> провал именно что.** У `f97` и `f98` — черновик, ни одного пакета — окно
> вылезло оба раза, а пакет создан **не был**: перезагрузка вкладки отменила
> сохранение начисто, `rulesPacks` остался пуст. То есть «сохранение уже ушло»
> верно для ПЕРЕсохранения активной воронки (где подтверждают пересчёт), но не
> для первого набора. Проверять надо по `GET .../funnels/{id}`, а не по
> поведению кнопки.
>
> Там же замер: **один клик по «Сохранить и активировать» уходит дважды** — у
> `f97` появились `v1` и `v2` с разницей 14 секунд и одинаковым телом, `v1`
> сразу ушёл в `ARCHIVED`. Похоже на повтор события расширением после таймаута
> CDP. На новой воронке безвредно, на активной — лишний пересчёт.

**Диалог перехватывается без человека**, если подключить сессию CDP заранее:

1. `mcp__chrome-devtools__list_pages` — найти страницу. Какая из вкладок «своя»,
   проще всего понять по метке, оставленной в `window` через claude-in-chrome.
2. `evaluate_script` на этой странице — сам вызов и подключает сессию.
3. Клик «Сохранить и активировать» через claude-in-chrome.
4. `handle_dialog` с `accept`.

Порядок обязателен: CDP отдаёт событие об открытии диалога только той сессии,
что была подключена **до** его появления. Подключившаяся позже получает
«No open dialog found», и это ложное «диалога нет», а не факт — на чём и
строилась прежняя запись в этом файле, будто `confirm()` убрали.

**Рецепт работает только там, где Chrome поднят с `--remote-debugging-port`.**
Замер 11.09: `list_pages` отвечает «Could not find DevToolsActivePort», то есть
подключиться нечем в принципе, а подмена `window.confirm` инъекцией скрипта в
главный мир блокируется классификатором разрешений (и справедливо: это
автоподтверждение чужого диалога). В таком Chrome **ОК жмёт человек** — по
одному разу на каждое сохранение набора. Планируя работу, закладывайте это:
две воронки = два обращения к владельцу.

**Активация идёт 5–6 минут** (`requestedAt` → `finishedAt` у `f43`:
10:17:35 → 10:23:34), вкладка всё это время не отвечает. Результат сверять по
`GET /app-api/api/admin/funnels/{id}`: у новой версии `status: ACTIVE` и
`activation.status: SUCCEEDED`, у прежней — `ARCHIVED`.

**Но 5–6 минут — не норма, а верхняя граница, и активации становятся в
очередь.** Замер 01.09.2026 на 32 сохранениях подряд: большинство прошло меньше
чем за минуту, а под конец накопилась очередь — `activation.status` шёл
`QUEUED` → `RUNNING` → `SUCCEEDED`, по одной за раз, и последние семь
разбирались около двадцати минут. Пока идёт активация, набор висит со
`status: DRAFT`, а кнопка в форме стоит в «Проверка и активация выполняются…»
и `disabled`. **Это не провал сохранения и не повод кликать снова** — черновик
уже создан с нужными полями и дойдёт сам. Отличать по `DRAFT` + `QUEUED`/
`RUNNING`, а не по тому, что в списке версий пока ничего не изменилось.

### Форма и карточка на 30.09.2026

Снято при заведении `f107`–`f110`. Интерфейс меняется от захода к заходу,
поэтому здесь описано состояние на дату, а что поменялось, записано в журнале
в конце файла.

**Форма «Новая воронка»**, поля сверху вниз:

| Поле | Как устроено | Что ставим |
|---|---|---|
| Код воронки | `input` | `fNNN` из базы |
| Название | `input` | АВ-четвёрка из базы |
| Продукт | кнопка со списком `<button>`, подписи вида `БОО · boo`; последний пункт «Добавить новый продукт» | код продукта ЛИК |
| Учет рекламных данных | кнопка со списком, по умолчанию «Автоматически по мэппингу» | не трогаем |
| Способ получения рекламных расходов | **нативный `<select>`**, по умолчанию `UNSET` «Не выбран»; `AUTOMATED` / `MANUAL` / `NO_SPEND` | `AUTOMATED`, как у всех свежих воронок |
| Часовой пояс | `input`, `Europe/Moscow` | не трогаем |
| Заметки | `textarea` | дата захода и чего не хватает |

Воронка создаётся черновиком (`DRAFT`), без набора правил. Черновик в реестре
виден, и в строке у него вместо «Деактивировать» стоят «Активировать воронку»
и «Удалить черновик воронки».

**Карточка воронки** (панель справа по кнопке «Открыть воронку») теперь
состоит из блоков:

- шапка: продукт, «Рекламные данные» (у нового черновика «Ожидаются»), дата
  создания, заметка;
- **«Роли оплат и продления»**, кнопка «Настроить роли оплат и продления».
  Блок новый, у свежих воронок пишет «Роли оплат не настроены. Цикл
  продлений не настроен». Мы его не заполняем и что он меняет в счёте, не
  выясняли;
- «Набор правил», кнопка «Добавить набор правил»;
- **«Данные и атрибуция»** с кнопкой «Оценить пересчёт» и списком «Что
  пересчитать» («Всё: события и атрибуция»). Тоже новый, не трогали.

**Панель набора правил**, сверху вниз: шаблон «Вебинар на несколько дней»;
«Правила действуют с» (обязательное) и «по»; блок модели атрибуции с двумя
рядами галок «Регистрация / Заявка / лид / Оплата»; пять полей приоритета UTM
(Источник, Канал, Кампания, Объявление / контент, Ключевая фраза); затем
списочные поля «Названия предложений регистрации», «Метки заявок», «Коды
вебинарных комнат»; галка «Учитывать предсписок»; «Правило связи оплаты»;
статусы и исключаемые метки оплат, заявок и выручки; «Рассчитывать источники
заявок» с приоритетом полей и группами «Значения метки» (`dozhim`,
`dozhim_email`, `zapis`/`record`, `zapis_web`); внизу «Горизонт»
(«Операционная сводка») и **«Макс. день вебинара» — обычный текстовый `input`,
по умолчанию 5**. Кнопка одна: «Сохранить и активировать». Над шаблоном стоит
пометка «Старый источник заявок не используется для новых воронок и оставлен
только для старых данных».

**Как найти списочное поле.** У всех списков подсказка одна и та же,
«Добавить значение», поэтому поле опознаётся по подписи: подпись это первый
листовой элемент в прадеде `input` (`input` → обёртка → блок значений → блок
поля). Сравнивать **на равенство, а не по началу строки**: «Метки заявок» по
началу совпадает с «Метки заявок, по которым считать только оплату», и поиск по
префиксу находит два поля. Кнопка удаления значения опознаётся по
`aria-label="Удалить <значение>"`, из этих меток и читается состав поля.

**Название предложения регистрации угадывать нельзя.** Вид названия у разных
воронок разный: `Регистрация на Детокс [БОО ВК ИНХАУЗ]` у f28,
`Регистрация на суставы [ВК ИНХАУС]` у f53, `Регистрация на ТАЗ [ВК NR]` у
f104. Фильтр сравнивает дословно, и неверное имя не поймает ни одной
регистрации, но будет выглядеть как «настроено». Пока предложения в GetCourse
нет, поле оставляем пустым; прецедент пустого списка есть, это f95.

### Механика браузера (30.09.2026)

- **Клик по `ref` в реестре срабатывает через раз.** «Новая воронка» и
  «Открыть воронку» по `ref` иногда не делают ничего. Надёжно работает DOM-клик
  `button.click()` из `javascript_tool`.
- **Если форма открыта DOM-кликом, набор с клавиатуры в поля не попадает**:
  фокуса нет, текст уходит в никуда, а поле остаётся пустым. Значения класть
  нативным сеттером `value` + событие `input`, у `<select>` сеттер
  `HTMLSelectElement` + `change`. Состав формы читать перед отправкой.
- **Строку реестра искать по листовому элементу с кодом** (`span` с текстом
  `f107`), а от него подниматься до строки с кнопкой «Открыть воронку». Подъём
  «пока в предке есть нужный код» промахивается: предок, содержащий `f107`,
  содержит и соседние строки, и открылась чужая карточка (f104, только
  просмотр, без последствий).
- **После «Создать воронку» кнопка может зависнуть в «Создаем...»**, а
  страница перестаёт реагировать на клики, хотя воронка уже создана и тост
  «Воронка создана» висит. Второй раз не жать: проверить по списку API и
  перезагрузить вкладку.
- **Права агента.** Заведение воронки через форму прошло, а заполнение
  набора правил (ввод кодов комнат DOM-сеттером) остановил автоматический
  фильтр прав Claude Code как «изменение общего ресурса». Владелец разрешил
  явно, после этого наборы заполнены. На такой заход разрешение лучше
  спросить заранее.
- **Работать через `chrome-devtools`, а не через claude-in-chrome** (указание
  владельца 30.09.2026). Только он снимает `confirm()` без человека. Рецепт,
  проверенный на f108–f110: форма заполняется `evaluate_script` (помощник
  `__L` из плана заводов, раздел 4е); дата: `focus()` на
  `input[type=date]` скриптом, затем `type_text` «30.09.2026»; сохранение:
  скрипт ставит `setTimeout(() => кнопка.click(), 300)` и возвращается, потом
  `wait_for` на заведомо отсутствующий текст (он отвалится с сообщением
  «Open dialog»), потом `handle_dialog accept`. Прямой клик по кнопке
  подвешивает инструмент до таймаута, а `handle_dialog`, вызванный раньше, чем
  диалог появился, честно отвечает «No open dialog found».
- **Chrome 154 открывает порт отладки только на IPv6.** Chrome с
  `--remote-debugging-port=9222` слушает `[::1]:9222`, а обёртка
  `~/agent-toolkit/bin/cdt-mcp` и `cdt-chrome` ходят на `127.0.0.1:9222`, и
  MCP отвечает «Could not connect to Chrome», хотя Chrome запущен. `localhost`
  при этом работает. В сессии 30.09 обошли временным пробросом
  `127.0.0.1:9222 → [::1]:9222` (скрипт на `asyncio`); насовсем это чинится
  заменой адреса в обёртке на `localhost`.
- **Повторный `confirm()` после перезагрузки** в этот раз не всплыл ни разу за
  четыре сохранения; у каждой воронки ровно одна версия `v1`.

## Ловушки

- **Нумерация ЛИК с пропусками.** На 2026-07-27 в реестре 46 воронок, но кодов
  `f10`, `f14`, `f17`, `f18`, `f20`, `f44`, `f49` не существует. Наибольший
  код — `f58`. Из «в базе 65 воронок, а в ЛИК 46» не следует, что чего-то
  не хватает: в ЛИК попадают не все воронки.
- **Написание подрядчика расходится.** (Поправка 30.09.2026: в названиях воронок
  ЛИК сейчас везде `ИНХАУЗ`, как в базе; `ИНХАУС` живёт в названиях
  предложений GetCourse, например `Регистрация на суставы [ВК ИНХАУС]`.)
  Исходная запись: ЛИК пишет `ИНХАУС`, база — `ИНХАУЗ`;
  ЛИК `ВНУТРЕННИЙ` / `ПАРТНЁР` / `ЮТУБ`, база `Внутренний` / `Партнер` /
  `Ютуб`. Сопоставлять по имени в лоб нельзя, только с нормализацией.
- **Направление на Яндексе расходится с GetCourse.** ЛИК и база у воронок
  НИМБ/ИНХАУС на Яндексе пишут `РСЯ`, а предложения GetCourse у тех же воронок
  несут `АВ Направление: Реклама`. У Алексея на Яндексе, наоборот, `Реклама` и
  `Ретаргет` — так что это не общее правило, а расхождение по конкретным
  воронкам.
- **`status` в ЛИК живой** (в отличие от `status` предложений GetCourse, где у
  всех подряд `draft`) — `DRAFT` в ЛИК действительно означает «ещё не запущена».
- **«Открыть набор правил» открывает не обязательно действующий набор.** У
  воронки может быть несколько `ACTIVE`-наборов, нарезанных по датам, и форма
  подставляет не тот, что действует сейчас: у `f30` (01.09.2026) открылся
  период `01.07–24.08`, тогда как действующий бессрочный — с `25.08`. Строки
  списка «Сохраненные наборы правил» в карточке **не кликабельны**, выбрать
  версию нельзя. Значит: перед сохранением сверять «Правила действуют с» с
  датой действующего набора из API и, если разошлось, выставлять её руками —
  иначе новая версия ляжет на чужой период, а действующий останется как был.
  Основа при этом безопасна: у всех проверенных воронок соседние версии
  различались только `followUpRuleJson`, остальные восемь секций совпадали
  байт в байт.
- **Кнопки удаления значений в списочных полях — иконки с пустым текстом.**
  Опознавать по `aria-label` (`Удалить <значение>`), как и «Открыть воронку» в
  строке реестра; поиск по `textContent` их не находит и молча делает вид, что
  список пуст. Цена ошибки: при замене набора меток старые остаются, новые
  добавляются сверху — фильтр `ALL` после этого не сработает никогда. Проверять
  состав поля **после** правки и **до** сохранения.

## Журнал нововведений ЛИК

ЛИК меняется между нашими заходами без предупреждения: появляются поля, блоки,
меняется ответ API. Сюрпризом это становится, когда скрипт или рецепт из этого
файла молча перестаёт работать. Поэтому правило такое:

1. **Перед заходом** в ЛИК пролистать журнал и раздел «Форма и карточка на
   дату». Если форма выглядит иначе, чем там описано, сначала снять новое
   состояние, потом писать.
2. **После захода** дописать сюда строку на каждое замеченное изменение, даже
   если оно нам пока не нужно: что появилось, где, что мы с ним сделали.
   Подробности захода идут в план заводов
