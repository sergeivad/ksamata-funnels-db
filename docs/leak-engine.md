# LeakEngine — приёмник f-кодов воронок

**LeakEngine** (`https://leak.besales.ai`) — внешняя система атрибуции, экран
«Воронки / Правила» (`/funnels/rules`).

## Правило нумерации (действует с 2026-08-04)

**F-код назначает база. ЛИК его принимает.**

Порядок работы: новая воронка заводится **сначала в базе** и сразу получает
код — `max(front_code) + 1` по этой базе (`nextFrontCode`,
[app/src/lib/front-code.ts](../app/src/lib/front-code.ts)). Затем владелец
переносит воронку в ЛИК **под тем же кодом**.

Пустой код при заведении — больше не норма: он был обходом, пока эталон был
на той стороне.

Что не изменилось и меняться не должно:

- **`max + 1`, а не первая дыра.** Дыры (`f10`, `f14`, `f17`, `f18`, `f20`,
  `f44`, `f49`, …) — чужие номера, занятые в ЛИК раньше; переиспользовать их
  нельзя. Максимум считается по обеим сторонам: если в ЛИК код выше нашего
  (воронку завели там напрямую), берём выше него.
- **Код не выводится из `num`.** `num` — внутренний ключ, к нумерации F
  отношения не имеет. Именно так появились `f64`–`f72`: 2026-07-26 им
  проставили «следующие свободные» по `num`, и коды сели на чужие номера.
- **Уникальный индекс (Phase-7) не даёт завести две воронки с одним кодом**
  даже случайно.

Заведение воронки в админке подставляет код автоматически — теперь это не
подсказка, а рабочее значение; переопределять его нужно только если ЛИК уже
занял этот номер.

### Что было раньше

- **2026-07-19:** «воронки нет в ЛИК → код пустой». Осторожно, но воронки
  месяцами жили без кода.
- **2026-07-28:** «есть в ЛИК → берём оттуда; нет → `max + 1`». ЛИК считался
  источником истины, база подстраивалась.
- **2026-08-04:** источник истины — база. Причина простая: воронка появляется
  у нас раньше, чем в ЛИК, и ждать чужого номера означает держать её без кода
  ровно столько, сколько до неё не дойдут руки.

**Писать в ЛИК — только по прямой просьбе владельца** (см. «Как завести
воронку»): активация набора правил запускает пересчёт заявок.

**Воронки в ЛИК не выключаем — никогда** (решение 2026-08-04). Расхождение
«у нас `archive`, в ЛИК `ACTIVE`» расхождением не считается.

## Как забрать список

Внутренний API отдаёт весь реестр одним запросом, но **только по сессионной
куке** — токена нет, поэтому запрос делается из вкладки уже залогиненного
браузера, через Chrome MCP (`mcp__claude-in-chrome__*`), не через `curl`.

1. Открыть вкладку: `navigate` → `https://leak.besales.ai/funnels/rules`
2. Выполнить в контексте страницы (`javascript_tool`):

```js
const r = await fetch('/app-api/api/admin/funnels', {credentials:'include'})
              .then(r => r.json());
r.funnels.map(f => [f.funnelCode, f.funnelName, f.productCode, f.status]);
```

Ответ — объект с ключом `funnels`. Поля, которые нужны на практике:

| Поле | Что это |
|---|---|
| `funnelCode` | `f6`, `f27`, … — то, что кладём в `front_code` |
| `funnelName` | у воронок начиная с `f27` это буквально АВ-четвёрка «Продукт / Подрядчик / Канал / Направление»; у `f6`–`f26` — легаси-описание |
| `productCode` | внутренний код продукта ЛИК (`boo`, `dbo`, `zkt`, `shzh`, …), с продуктами базы не совпадает |
| `status` | `ACTIVE` / `INACTIVE` / `DRAFT` |
| `rulesPacks[]` | наборы правил атрибуции; `registrationRuleJson`, `applicationRuleJson`, `attendanceRuleJson` — эталон по тегам заявок, рег-офферам и кодам вебинарных комнат |

Соседние эндпоинты той же админки: `/app-api/api/admin/products`,
`/app-api/api/auth/session`.

## Как завести воронку

Проверено 2026-08-02: так заведены `f73`, `f74`, `f78`. Всё — тем же
`fetch` из залогиненной вкладки, `credentials:'include'`.

Заведение — **два шага**: сама воронка и набор правил к ней. Воронка без
набора правил ничего не считает.

### 1. Воронка

```js
POST /app-api/api/admin/funnels
{ "funnelCode": "f78", "funnelName": "ТКМ / NR / ВК / Реклама",
  "productCode": "tkm", "businessTimezone": "Europe/Moscow", "status": "DRAFT" }
```

`productCode` берётся из `/app-api/api/admin/products` и с продуктами базы не
совпадает: ТКМ там `tkm` с отображаемым именем «КОД МОЛОДОСТИ», ЖИВО — `jivo`
на всю линейку (`ЖИВО-суставы`, `ЖИВО-ЖКТ`, `ЖИВО-суставы-триал` — один
`productCode`, различает их только `АВ Продукт` в метках).

### 2. Набор правил

```js
POST /app-api/api/admin/funnels/{funnelId}/rules-packs/save-and-activate
```

Тело — **поля формы, а не сырой rule-JSON**: сервер сам собирает из них
`registrationRuleJson`, `applicationRuleJson`, `attendanceRuleJson`,
`stageMapJson` и прочее. Руками эти блобы писать не надо.

| Поле | Значение |
|---|---|
| `templateKey` | `webinar_multi_day` — единственный используемый |
| `effectiveFrom` | `ГГГГ-ММ-ДД`, обязательное. **С этой даты ЛИК пересчитает заявки** |
| `effectiveTo` | можно не слать |
| `registrationOfferNames` | названия предложений регистрации; у «Прямых» — `[]` |
| `applicationTags` | АВ-набор этапа «Оплата»: маркер типа + `АВ Этап: Оплата` + четыре оси |
| `webinarRoomCodes` | коды комнат; у «Прямых» — `[]` |
| `maxPrimaryWebinarDay` | 5 у пятидневных, 3 у трёхдневных и у «Прямых» |
| `prelistApplicable` | `false` |
| `paymentLinkRule` | `payments.Заказ = deals.Номер` |
| `paymentSuccessStatuses` | `["Получен","Списание с баланса"]` |
| `paymentExcludedStatuses` | `["Ожидается","Возвращен","Начислен на депозит"]` |
| `paymentBridgeAllowedExcludedApplicationOrderTags` | `["дубль"]` |
| `applicationExcludedTags` | `["дубль","тест"]` |
| `applicationExcludedStatuses` | `[]` |
| `firstPayExcludedTags` | `["дубль","тест","2-й платеж","3-й платеж","полная оплата"]` |
| `cashRevenueExcludedTags` | `["дубль","тест"]` |
| `analysisHorizon` | `live_operational` |

Всё, кроме первых шести строк, у всех воронок ЛИК одинаково — форма
подставляет эти значения сама, и отличаться там ничего не должно.

### 3. Активация воронки

```js
PATCH /app-api/api/admin/funnels/{funnelId}   { "status": "ACTIVE" }
```

Без подтверждения и без пересчёта.

### ⚠️ Подтверждение пересчёта — только в интерфейсе

`save-and-activate` в интерфейсе закрыт нативным `confirm()`: «Активировать
правила с {дата}? Система найдёт ограниченный набор заказов за этот период и
точно пересчитает заявки». **Вызов API идёт мимо этого окна** — окно рисует
клиент, а не сервер. Ограничитель на сервере есть (активация останавливается,
если превышены безопасные лимиты), но дату спрашивать всё равно надо у
владельца: она задаёт окно пересчёта.

Побочно: пока это окно открыто, вкладка не отвечает, и CDP валится по таймауту
с «renderer may be frozen». Это не зависание — это ждущий `confirm()`.

## Ловушки

- **Нумерация ЛИК с пропусками.** На 2026-07-27 в реестре 46 воронок, но кодов
  `f10`, `f14`, `f17`, `f18`, `f20`, `f44`, `f49` не существует. Наибольший
  код — `f58`. Из «в базе 65 воронок, а в ЛИК 46» не следует, что чего-то
  не хватает: в ЛИК попадают не все воронки.
- **Написание подрядчика расходится.** ЛИК пишет `ИНХАУС`, база — `ИНХАУЗ`;
  ЛИК `ВНУТРЕННИЙ` / `ПАРТНЁР` / `ЮТУБ`, база `Внутренний` / `Партнер` /
  `Ютуб`. Сопоставлять по имени в лоб нельзя, только с нормализацией.
- **Направление на Яндексе расходится с GetCourse.** ЛИК и база у воронок
  НИМБ/ИНХАУС на Яндексе пишут `РСЯ`, а предложения GetCourse у тех же воронок
  несут `АВ Направление: Реклама`. У Алексея на Яндексе, наоборот, `Реклама` и
  `Ретаргет` — так что это не общее правило, а расхождение по конкретным
  воронкам.
- **`status` в ЛИК живой** (в отличие от `status` предложений GetCourse, где у
  всех подряд `draft`) — `DRAFT` в ЛИК действительно означает «ещё не запущена».
