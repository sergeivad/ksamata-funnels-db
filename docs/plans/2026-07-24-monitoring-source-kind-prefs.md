# Мониторинг: предпочтение по группе + понятные подписи

Дата: 2026-07-24. Статус: в работе.

## Задача

1. Новая ссылка, появившаяся в блоке воронки, должна попадать под проверку сама —
   если группа этого вида уже включена.
2. Подписи чипов групп на `/monitoring` — по-русски и так, чтобы числа читались
   без догадок.

## Что уже работает и менять не надо

`syncMonitorTargets()` запускается в начале **каждого** цикла
(`monitor-run.ts:153`) — и планировщика (раз в `MONITOR_INTERVAL_MINUTES`,
по умолчанию 15), и кнопки «Проверить сейчас». Он заново пересобирает все URL
из `funnel_block_items` и поля `funnels.landing_url`. Новая воронка и новый блок
заводят цели сами, без ручного вмешательства.

## Проблема

«Включено по умолчанию» — константа в коде (`LANDING_SOURCE_KINDS`), а клик по
чипу группы правит `enabled` + `manual_override` только у тех целей, что
существуют на момент клика. Поэтому:

- включили группу `tariffs` сегодня → 109 целей получили `manual_override = 1`;
- завтра в новой воронке появился 110-й тариф → цель заводится с
  `enabled = 0`, потому что `tariffs` нет в `LANDING_SET`.

Решение группы нигде не хранится, наследовать его новым целям неоткуда.

## Решение: хранить решение на уровне группы

Новая таблица (одна строка на вид источника):

```sql
CREATE TABLE IF NOT EXISTS monitor_source_kind_prefs (
  source_kind TEXT    PRIMARY KEY,
  enabled     INTEGER NOT NULL DEFAULT 0,
  updated_at  TEXT    NOT NULL DEFAULT (datetime('now'))
);
```

Живёт в `PHASE6_DDL`, а не в отдельной Phase-7: это таблица мониторинга, DDL уже
идемпотентен (`IF NOT EXISTS`) и уже прогоняется в Docker-энтрипойнте. Новая
фаза потребовала бы раннера, сборки `.cjs` и правки энтрипойнта ради одной
таблицы.

`groupDefault(kind)` = строка из таблицы, а если строки нет — прежнее правило
(`landings` и `funnel_landing_url` включены, остальные выключены). Значит
миграция ничего не переносит: до первого клика поведение ровно то же, что
сейчас.

Три места переходят с константы на `groupDefault(kind)`:

| Место | Было | Стало |
|---|---|---|
| `syncMonitorTargets`, новая цель | `LANDING_SET.has(kind)` | `groupDefault(kind)` |
| `syncMonitorTargets`, старая цель без `manual_override` | пересчёт из `LANDING_SET` | пересчёт из `groupDefault(kind)` |
| `setTargetEnabled` / `setSourceKindEnabled` | сравнение с `LANDING_SET` | сравнение с `groupDefault(kind)` |

`setSourceKindEnabled` дополнительно:

- пишет строку в `monitor_source_kind_prefs`;
- ставит `manual_override = 0` всем целям этой группы.

Групповое решение перебивает точечные тумблеры внутри группы. Иначе «включить
группу» оставляло бы дыры из ранее выключенных вручную целей, и объяснить их
пользователю было бы нечем. После клика по группе `enabled` = решение группы,
`manual_override` = 0, то есть новая семантика: override означает «эта одна цель
отличается от своей группы».

Инвариант авто-оживления сохраняется: цель, у которой `manual_override = 0`,
пересчитывается из группы на каждом синке, поэтому пропавший и вернувшийся URL
возвращается в проверку сам.

## Охват: только активные воронки

`collectTargets()` берёт URL только у воронок в статусе `active`
(`MONITORED_FUNNEL_STATUS`). Черновик ещё не запущен, архив уже отработал: их
страницы могут лежать на законных основаниях, и падения по ним — шум, из-за
которого перестают смотреть на настоящие.

Отдельного кода на снятие с проверки не нужно: URL, оставшийся только за
неактивными воронками, перестаёт собираться и попадает в общий авто-ретайрмент —
гаснет, отвязывается от воронок, сохраняет историю инцидентов и оживает сам,
когда воронку вернут в активные.

URL, который делят активная и архивная воронки, остаётся под проверкой, но в
`monitor_target_funnels` числится только за активной — иначе чипы «Воронки»
показывали бы архив.

## Подписи

Русские имена групп берём из `BLOCK_KINDS` (`src/lib/blocks.ts`) — тот же текст,
что человек видит в редакторе воронки. Второго списка не заводим, чтобы он не
разъехался. Отдельно только `funnel_landing_url` → «Лендинг воронки»: это поле
воронки, а не блок.

Новый модуль `src/lib/monitor-kinds.ts` с `sourceKindLabel(kind)`; неизвестный
вид отдаёт сам себя, чтобы UI не падал на данных из будущего.

Чипы: `Лендинги · 38 из 40`, `Ссылки / дашборды · 0 из 154`.

Над рядом чипов — одна поясняющая строка: что это группы и что клик включает или
выключает всю группу вместе с будущими ссылками.

Состояние чипа видно фоном: вся группа включена — акцентный, включена частично —
обычный, ни одной — приглушённый.

В таблице: третья строка ячейки «Страница» показывает тот же ярлык вместо голого
`landings`; заголовок колонки `С` → `Держится с` (односимвольный заголовок не
читается, а значение — момент, с которого статус не менялся).

## Тесты

`tests/monitor-targets.test.ts`:

- новая цель наследует включённую группу (это и есть требование задачи);
- клик по группе снимает точечный `manual_override` внутри группы;
- без строки в prefs поведение прежнее (ленды вкл, остальное выкл);
- авто-оживление пропавшего и вернувшегося URL продолжает работать.

Существующий кейс «включение группы не-лендов ставит override = 1» переписывается
под новую семантику: теперь клик по группе меняет дефолт группы, поэтому
`manual_override` остаётся 0.
